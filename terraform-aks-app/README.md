# terraform-aks-app

TP Java/Angular, piste "AKS": this learner's Container Registry (ACR) + the
AcrPull/AcrPush role assignments that let the shared cluster's nodes pull
images and let `ci_app_deploy` push them.

Depends on `../terraform-core` (VNet/storage not used directly here, but
`ci_app_deploy`'s principal ID is — read via `terraform_remote_state`, see
`main.tf`) and `../terraform-shared-aks` (the AKS cluster, looked up by name
via a data source — no state coupling). Apply `terraform-core` first; the
shared cluster must already exist.

Independent of `../terraform-python` and `../terraform-managed-services` —
this track can be applied, destroyed, or left off entirely without touching
either of the other two. Note, though, that the backend this track deploys
(`azure-quiz-backend`'s `deploy-aks.yml`) connects to the SAME Postgres/Redis
instances `../terraform-managed-services` creates — see that directory's
README for why the two states still stay independent despite the sharing.

## What this does NOT do

Creating the Kubernetes namespace on the shared cluster, and granting
`ci_app_deploy` the namespace-scoped Azure RBAC role to deploy into it, both
need rights this directory's identity doesn't have (they're scoped to the
*shared* cluster's Resource Group, not this learner's own). The trainer runs
`scripts/bootstrap-aks-namespace.sh` once per learner instead — see `main.tf`'s
header comment and `../terraform-shared-aks/README.md`.

## Setup

1. `../terraform-core` must already be applied, and `../terraform-shared-aks`
   must already have a cluster for `var.environment`.
2. Create the HCP Terraform Cloud workspace `azure-aks-app-alderic-hoarau`,
   Execution Mode **Local**.
3. `terraform init && terraform plan` — review, then `terraform apply`.
4. Ask the trainer to run `scripts/bootstrap-aks-namespace.sh` for you
   (needs `terraform output` from `../terraform-core`'s
   `ci_app_deploy_principal_id`).
